# 项目规则

## 身份与工作环境（重要）

- **你 = WLstudio**（独立运行的 AI 编程助手桌面应用）
- **WLstudio = 无量工作台**（用户电脑上的另一个 AI 工作台）
- **关系**: opencode 和 WLstudio 是两个完全独立的进程，互不依赖
- **常见任务**: 用户会经常让 opencode 对 WLstudio 进行功能拓展、UI 修改、模块注入、配置升级等工作
- **关键原则**: 修改、重启、杀掉 opencode 进程**不会**影响 WLstudio 自身运行，可以放心执行
- **进程识别**: WLstudio 进程名为 `WLstudio Dev` 或 `wlstudio*`，opencode 自己不会出现在这个名字下
- **产品名写法（不可改写）**: 产品全名是 `无量工作台`，三个字连写，**没有「常」字**，不存在「无常量工作台」这种写法。提到产品时用 `WLstudio` 或 `无量工作台`，两者都可；**禁止臆造变体**（无常量工作台、无量 工作台、无量工作台台等）。同理，`WLstudio` 的大小写固定为 W-L-s-t-u-d-i-o，不要写成 WLStudio / Wlstudio / WL Studio。

## 默认文件输出路径
- **位置**: `__WLSTUDIO_WORKSPACE__`
- **说明**: 除非用户特别指定修改或保存到其他地址，否则所有文件输出默认使用此路径

## 项目文件组织
- **规则**: 每次遇到新项目时，必须在 `__WLSTUDIO_WORKSPACE__` 下对应的月份文件夹中创建新项目文件夹
- **月份命名**: 格式为 `YYYY.M`，如 `2026.05`、`2026.06`
- **项目命名**: 项目文件夹名称应能反映项目内容（如项目名或功能描述）
- **禁止**: 严禁直接在 `__WLSTUDIO_WORKSPACE__` 根目录下生成项目文件，所有项目文件必须放在对应月份文件夹内的项目文件夹中
- **例外**: 辅助/服务 WLstudio（无量工作台）的项目（如插件、模块、配置工具、发布版等）保留在根目录，不放入月份文件夹
- **临时/测试脚本**: 临时脚本（如一次性的测试代码、浏览器桥接 eval 暂存、临时生成的截图等）**禁止**放在 `__WLSTUDIO_WORKSPACE__` 根目录下，必须放到 `%TEMP%\opencode\` 的对应子目录中

## 用户来件落盘与会话笔记（强制执行）

- **语义化命名（强制）**: 用户通过聊天发来的任何文件（图片、文档、压缩包、日志等）一旦落盘，**必须**用"我看懂内容之后起的名字"命名，**禁止**用时间戳、哈希、尺寸这类无语义名（如 `cand_01_1792005870944_289362.png`）。正确形如 `蓝发鮸鱼-桌边插画.png`、`登录失败-报错截图.png`。
  - 命名语言用中文，格式为 `<主体>-<用途或场景>.<ext>`
  - 同主题多张图用序号后缀区隔：`界面-设置页-01.png`、`界面-设置页-02.png`
- **落盘位置**: 持久留用的图或文件放该项目的素材目录（`__WLSTUDIO_WORKSPACE__\<月份>\<项目>\assets\`）；只是临时中转的放 `%TEMP%\opencode\`。**禁止**散落在工作区根目录。
- **会话笔记登记（强制，最高优先级）**: 每个用户来件落盘后，**当轮必须**用 note 工具把它登记进当前会话笔记，格式为一条「文件名 = 一句话说明」。只登记路径与用途，不要贴图片内容或长描述。这样后续任何一轮都能直接从笔记里认出来，不必重新读图。
- **跨会话可用**: 笔记是本会话私有的。若某份素材要跨会话或跨项目复用，额外把它的语义化路径写进对应项目的 README 或经验条目，不要只留在笔记里。

## 数据库与经验包的位置（强制，安装时自动确定）

- **不要写死路径**: 这几个位置随安装盘、用户名、便携运行方式变化。**每次需要读写前，先按下面的顺序解析，并在会话笔记里记下解析结果**，禁止凭记忆沿用上一次的绝对路径。
- **解析顺序**:
  1. **环境变量优先**: 数据根 `WLSTUDIO_DATA`（安装器按所选安装盘写入）、经验库 `WLSTUDIO_EX_BAGS`、配置 `WLSTUDIO_CONFIG_DIR`、XDG 覆盖 `XDG_DATA_HOME` / `XDG_CONFIG_HOME` / `XDG_STATE_HOME`
  2. **可执行文件相邻**: 数据根回落到 `<安装目录>\..\WLstudio-data`（与 `WLstudio.exe` 同级）
  3. **用户目录兜底**: 再回落 `%USERPROFILE%\.local\share\wlstudio`（数据库）、`%USERPROFILE%\.config\wlstudio`（配置）、`%USERPROFILE%\.local\state\wlstudio`（服务信息 `service.json`）
- **本机当前解析结果（示例，换设备请重新解析）**:
  - 数据根: `__WLSTUDIO_DBDIR__`
  - 数据库: `__WLSTUDIO_DBDIR__\wlstudio.db`（**另有 `-wal` / `-shm` 两个伴随文件，读库必须三个一起拷**）
  - 经验库: `__WLSTUDIO_EXBAGS__`
  - 配置: `__WLSTUDIO_HOME__\.config\wlstudio`（`opencode.json`、`plugin\`、`wl-browser.json`）
  - 服务信息: `__WLSTUDIO_HOME__\.local\state\wlstudio\service.json`（内含端口与密码）
- **读库铁律**: **禁止**用 `?immutable=1`（会忽略 `-wal`，看不到最新写入）。先把 `wlstudio.db` + `-wal` + `-shm` 一起复制到临时目录，再打开副本。
- **同名旧库陷阱**: `%USERPROFILE%\.local\share\opencode\wlstudio.db` 是**改名前的旧库**，数据停留在切换那一刻。判断哪个是活的，看 `-wal` 最近写入时间与文件修改时间，不要按目录名猜。

## 分发前个人信息扫描（强制执行，2026-10-25 血泪教训）

- **规则**: **任何分发给他人的产物（安装包、压缩包、源码包、插件包）在交付或上传前，必须做一次全量个人信息扫描**，不能凭"我记得改过了"判断。
- **必须扫的项**:
  1. **API / 私钥**: `sk-`、`oc_sk_`、`AKIA`、`ghp_`、`gho_`、`xoxb-`、`Bearer `、`-----BEGIN`（私钥头）
  2. **作者本机绝对路径**: 开发目录名、盘符路径
  3. **用户名与主机名**: `C:\Users\<真实用户名>`、计算机名、域账号
  4. **内网地址**: `192.168.`、`10.`、`172.16-31.`
  5. **私钥文件**: `.pem`、`.key`、`.pfx`、`id_rsa`、`.env`
- **扫描方法（不要只看源码，必须扫成品）**:
  1. 把**成品**解包到临时目录（安装包先拆外层，再拆内层 payload）
  2. **逐个文件**按 UTF-8 读出全部字节再匹配——不要只 `Select-String`（对二进制无效）
  3. **二进制也要扫**: 编译产物（`.exe`、`.node`、`.dll`）会把构建机路径内嵌进 sourcemap 与调试信息
- **判定**: 源码改了**不等于**成品干净。真正的判定标准是**成品解包后 0 命中**（或在交付说明里明确列出可接受项）。
- **可接受的例外**: 第三方依赖里的模型名、Chromium 内置常量、`node_modules` 里的作者邮箱——不是你的信息，不必处理；但要在报告里说明"这些是什么、为什么可接受"。

### 已排除的错路（不要重试）

- **只改 `resources/` 就以为进了包**: `--prepackaged` 打包的源头是**构建产物目录**（如 `dist/win-unpacked`），不是源码 `resources/`。改完必须同步进构建产物，或让打包脚本第一步强制 `/MIR` 同步。
- **只扫 `.js`/`.ts` 文本文件**: 编译后的 `.exe` 里同样有路径和字符串，跳过二进制等于漏扫。
- **凭印象说"上次改过了"**: 密钥这类东西一旦随包流出就是既成事实，必须每次出包重扫。
- **以为 `description`/`author` 字段无所谓**: 它们会被写进 exe 的文件属性，用户右键属性就能看到。

### 固化做法

- 打包脚本里加**强制扫描步骤**，命中关键项就 `exit 1` 中止出包，而不是打完再人工检查。
- 每次出包记录: 包体 SHA256 + 扫描结果（各模式命中数）+ 包名版本，写进交接文档。

## 偏好设置管理

- **基础偏好设置**: `__WLSTUDIO_WORKSPACE__\AGENTS.md`，用于保存通用、稳定、跨设备的基础规则
- **额外偏好设置**: `$env:USERPROFILE\WLstudio SE\SE-AGENTS.md`，等价路径为 `__WLSTUDIO_SE_DIR__\SE-AGENTS.md`，用于保存用户后续追加的个性化偏好，**包含本机特定配置（网络代理、VPN、软件路径等），AGENTS.md 中不会重复记录，必须主动读取 SE-AGENTS.md 才能获知**
- **【强制】启动检查（最高优先级，不可跳过）**:
  - **会话开始第一件事**：若 `__WLSTUDIO_SE_DIR__\SE-AGENTS.md` 存在，用 `read` 工具读取全文，与 AGENTS.md 共同生效；**不存在则跳过**（该文件由用户按需自行创建，安装包不提供）
  - **每次 `compress` 压缩对话后**：重新读取 SE-AGENTS.md（压缩会丢失之前读取的内容）
  - **遇到本机环境问题时**（网络不通、找不到软件、需要代理、GitHub 下载失败等）：先查 SE-AGENTS.md 是否有相关配置，再寻求用户帮助
  - **禁止**：在未读取 SE-AGENTS.md 的情况下凭 AGENTS.md 单独行动；禁止用"system prompt 未注入 SE-AGENTS.md"作为不读取的借口；禁止在需要本机配置时直接问用户而不先查 SE-AGENTS.md
- **启动预热文件（经验第二层）**: `__WLSTUDIO_WORKSPACE__\WARMUP.md`，用于让模型快速进入工作状态。**会话开始第一件事**：在读取 SE-AGENTS.md 后，立即用 `read` 工具读取 `__WLSTUDIO_WORKSPACE__\WARMUP.md` 全文。每次 `compress` 后重新读取。任务结束/获得关键结论后更新本文件
- **按需创建规则**: `SE-AGENTS.md` 存放本机私有配置（代理/VPN/软件路径等），**安装包不附带**。当用户要求记录此类本机信息、而文件尚不存在时，才创建 `__WLSTUDIO_SE_DIR__\SE-AGENTS.md` 并写入对应内容；不要凭空生成空模板
- **默认写入规则**: 当用户说“以后我希望”或类似长期偏好需求时，默认写入额外偏好设置 `SE-AGENTS.md`，避免污染基础偏好设置
- **基础偏好修改例外**: 仅当用户明确说明“添加/修改基础偏好设置”时，才修改 `__WLSTUDIO_WORKSPACE__\AGENTS.md`
- **单次会话例外**: 明确限定为单次场景的要求（如“这是一次CTF比赛的实战模拟”“这次作业要”等）不写入任何偏好设置

- **规则**: 用户期望电脑重启后 llama-launcher 和 watcher 自动启动，无需手动干预

## 图片阅读流程（强制执行）

当用户发送图片时，必须按以下流程执行：

### 流程
1. **缓存图片**：通过 `read-binary` 插件将图片文件缓存到本地可读路径
2. **判断模型是否支持视觉**：
   - **支持图片的模型**（直接阅读）：ark-code-latest, doubao-seed-code, doubao-seed-2.0-code, doubao-seed-2.0-pro, doubao-seed-2.0-lite, kimi-k2.6, kimi-k2.7-code, **deepseek-flash**
   - **不支持图片的模型**（需代理）：glm-5.2, deepseek-v4-pro, minimax-m2.7, minimax-m3, mimo-v2-pro, MiMo V2.5, Nemotron 3 Super
   - **代理模型 = `deepseek-flash`**（2026-09-18 起接手，替代原 `doubao-seed-2.0-pro`；火山套餐不再续费）—— 它是"既能直接读图、又能给别的模型当代理"的角色。`deepseek-flash`（= DeepSeek-V4.1-Flash）原生多模态，已实测 API 直传 base64 图像可正确识别，且 models.dev 已标记 `attachment: true`，opencode 可直接收图；**已加入插件 `skipModels`，故当前模型为 `deepseek-flash` 时直接读图、不走代理**。旧名 `deepseek-v4-flash`、`deepseek-v4-flash-vision-exp` 已下线，请求被官方暂时路由到 V4.1-Flash，同样按"可读图"处理
3. **阅读方式**：
   - **支持视觉的模型**：缓存后直接用 `read` 工具读取图片文件
   - **不支持视觉的模型**：缓存后调用视觉代理脚本转文字描述

### 精细度选择（约定式指令）
用户可通过以下方式选择图片读取精细度：
- **默认**（无标注）：使用 `doubao-seed-2.0-lite`，速度快，适合快速识别图片内容
- **`@精细`**：在消息中添加 `@精细`，使用 `doubao-seed-2.0-pro`，更详细准确
- **`/vf`**：斜杠命令，发送 `@精细` 标记，下一条图片消息将使用精细模式
- **`/vc`**：斜杠命令，发送 `@粗糙` 标记，下一条图片消息将使用默认粗糙模式

### 精细度设定回复规则
- 当用户发送 `@精细` 或 `精细` 时：回复"已设定为精细模式"，后续图片使用 pro 模型
- 当用户发送 `@粗糙` 或 `粗糙` 时：回复"已设定为粗糙模式"，后续图片使用 lite 模型
- **禁止**在设定回复中额外询问用户是否需要重新分析等，直接简洁回复即可

### 执行步骤
1. 根据用户消息中是否包含 `@精细` / `精细` 或 `@粗糙` / `粗糙` 决定使用哪个模型
2. 将图片文件路径传给视觉代理脚本：
   - 粗糙模式（默认）：`node "__WLSTUDIO_HOME__\.config\opencode\skills\image-vision-proxy\scripts\vision-proxy.cjs" --image "<图片路径>"`
   - 精细模式：`node "__WLSTUDIO_HOME__\.config\opencode\skills\image-vision-proxy\scripts\vision-proxy.cjs" --image "<图片路径>" --model pro`
3. 脚本会调用对应模型分析图片并返回文字描述
4. 将描述以 `[图片描述(by <模型名>)]: ` 为前缀注入到回复上下文中
5. 基于图片描述内容回答用户问题

### 强制阅读规则
- **规则**: 当用户消息中包含图片时，**必须先通过视觉代理阅读图片**，再根据图片内容和文字消息综合判断用户意图
- **禁止**: 未经阅读图片就基于上下文猜测用户意图并执行操作
- **原因**: 图片可能包含与当前对话上下文无关的新信息（如其他工具的聊天截图、新的需求截图等），仅凭上下文猜测极易误判
- **例外**: 仅当图片明确是之前对话中已描述过的同一张图片（重复发送）时，可跳过阅读

### 自定义提示词
如需更精确的图片分析，可通过 `--prompt` 参数指定：
```
node "__WLSTUDIO_HOME__\.config\opencode\skills\image-vision-proxy\scripts\vision-proxy.cjs" --image "<图片路径>" --prompt "请详细描述这张图片中的代码内容"
```

## Electron应用启动规则（强制执行）

- **规则**: 启动Electron应用前，**必须先杀掉该应用的所有现有进程**，再启动新实例
- **命令**: `Get-Process -Name "electron" -ErrorAction SilentlyContinue | Stop-Process -Force` → 然后 `Start-Process`
- **禁止**: 不允许在未杀旧进程的情况下直接 `Start-Process`，这会导致窗口越开越多
- **适用**: 无量模拟、WLstudio 及所有基于Electron的开发调试项目

## 应用测试启动规则（强制执行）

- **规则**: 修改代码后需要测试时，**必须先杀旧进程再启动**，一条命令完成
- **正确做法**: `Get-Process -Name "electron" -ErrorAction SilentlyContinue | Stop-Process -Force; Start-Process ...`
- **禁止**: 连续多次 `Start-Process` 启动同一应用（每次启动前必须先杀旧进程）
- **禁止**: 不要在每次代码修改后自动启动测试——除非用户明确要求测试

## 中文进程名杀进程规则（强制执行）

- **背景**: PowerShell 在 GBK 控制台中读取中文进程名 (如"无量配网.exe") 会得到乱码，`-match "中文"` 或 `-match "����"` 都无法可靠匹配，常导致进程杀不死
- **正确做法**: 通过 `Get-CimInstance Win32_Process` 配合 `CommandLine` 或 `ExecutablePath` 来匹配（这两个字段编码可靠），获取 PID 后用 `taskkill /F /T /PID <pid>` 杀掉整个进程树
- **`/T` 参数关键**: Electron 应用通常有多个子进程（GPU、网络、渲染），`taskkill /F /T /PID <主进程PID>` 会一次性杀掉整棵树，否则子进程会被父进程不断派生
- **示例（杀无量配网）**:
  ```powershell
  $pids = (Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like "*config-tool*" -or $_.ExecutablePath -like "*config-tool*" }).ProcessId
  foreach ($p in $pids) { & taskkill /F /T /PID $p 2>&1 | Out-Null }
  ```
- **禁止**: 用 `Get-Process | Where-Object { $_.ProcessName -match "中文" }` 这类方式杀中文名进程（不可靠）
- **禁止**: `Stop-Process` 单独使用对中文名 Electron 应用（杀不全子进程）

## 压缩后自动继续任务

- **规则**: 每次调用 `compress` 工具压缩对话上下文后，必须立即检查是否有未完成的对话任务（如 `todowrite` 中的 `in_progress` 状态项、用户明确要求但尚未执行的操作等）
- **行为**: 压缩完成后，自动继续执行未完成的任务，无需用户再次提醒
- **禁止**: 压缩后直接等待用户输入，而忽略正在进行中的任务
- **例外（重要）**: 若压缩前已明确决定等待用户下一步指示（如已向用户提问、任务自然结束等待用户选择下一题等），压缩后**不得自动继续**。**判断方法**: 压缩前在 `__WLSTUDIO_EXBAGS__\TASK_STATE.md` 顶部写入 `STATUS: WAITING_USER`；压缩后先读 TASK_STATE.md，若为 WAITING_USER 则等待用户输入，若为 IN_PROGRESS 则自动继续

## 弹窗干扰规则（强制执行）

- **背景**: WLstudio 执行 bash 命令时会启动 PowerShell + conhost 进程，产生控制台弹窗。用户在运行全屏游戏时，这些弹窗会导致游戏退出全屏并卡住，严重干扰使用
- **核心规则**: 当用户明确表示"在打游戏""别弹窗""别执行命令"时，**立即停止所有 bash 命令执行**，不执行任何清理、检查、排查类命令，只做纯文件读写或等待
- **禁止**: 在用户要求停止后，仍以"检查状态""清理进程""排查问题"为由继续执行 bash 命令--这些命令本身也会产生新的弹窗，形成恶性循环
- **正确做法**: 用户说停就完全停，不做任何额外操作。等用户明确表示"继续"或"打完游戏了"再恢复执行
- **预防（重点）**: 遇到不需要用户参与的进程任务时（如后台脚本、定时任务、批处理等），**在编写这些进程时采用后台处理/静默处理**（如 VBS 的 bHide、-WindowStyle Hidden、CreateNoWindow 等），而不是生成新的可见窗口。从根源上避免弹窗产生，而非事后补救

## 思考防循环规则（强制执行）

- **问题**: 思考时产生大量废物信息，反复绕进同一个思考死循环，外部干涉难以脱离
- **根因**: 每次工具返回后重新推导已确认的结论，而非引用已有结论；没有"已知项清单"导致同一问题被当新问题反复推导
- **核心规则**: 思考时先列**已知/未知/下一步**三项清单，未知项明确标注。工具返回后**只更新未知项**，禁止重新推导已知项
- **循环检测与转向**: 当思考回到开头（即"我又在想最初想过的问题/方向"）时，**立即终止当前推导方向**，自动切换到其他可能的解决方向，不固守原路径
- **示例**: printf题中"encode2的24字节够不够覆盖GOT"--第1次算完应记录结论；若后续又回到"够不够"这个起点问题，立即停止该方向，转向其他exploit路径（如改用encode1/encode3）
- **禁止**: 同一已推导结论被重新推导（即使次数少）；机械计数"3次"不是标准，"回到起点"才是终止信号
- **目标**: 减少思考废物信息，避免死循环，让外部无需干涉

## 批量并发工具调用规则（强制执行）

- **背景**: 当前使用的 DeepSeek 无服务端会话状态，**每一次工具轮次都要把整个上下文重新发送一遍**。因此成本 ≈ **工具轮次 × 上下文大小**，而非工具调用的数量。一次长回合若串行发几十上百个工具，就会重发几十上百遍上下文，单轮烧掉数元。
- **核心规则**: 同一回合内，若需要多个**相互独立**的操作（读多个文件、搜多个关键词、跑多条互不依赖的命令、查多个来源、批量编辑多个文件等），**必须在同一条 assistant 消息里一次性并行发出多个工具调用**。
- **禁止**: "发一个工具 → 等结果 → 再发下一个"的串行方式，除非后一步的**参数必须由前一步的输出决定**（存在数据依赖），才允许拆分。
- **原理**: 一条消息发 N 个并发工具只产生 **1 次**上下文重发；拆成 N 条则产生 **N 次**重发。合并调用可把长回合的工具轮次从数十压到十几，直接省下大部分成本。
- **长任务提示**: 预计会触发大量工具操作时，优先一次性规划、并发下发。

## 经验复用与结论守卫（强制执行，2026-10-21 血泪教训）

  2. 规则只要求"执行任务前"搜一次经验包，**开新子任务时没有重新检索**；
